# Signup host dashboard and email alerts

View signups opens the published form's Host dashboard from its host toolbar, builder sharing section or main dashboard signup progress card. Owners and accepted co-hosts can see participant contacts, notes and answers. Guests receive only their own response and aggregate availability through the existing signup projection.

By item/shift is the initial view. Each item shows its time, quantities reserved, capacity remaining, waitlist quantities and assigned people. Clicking a name opens that person's signup. By person groups confirmed, waitlisted and cancelled responses, with two cards per row when the dashboard has at least 700px of usable width. Narrow layouts use one column. Pencil and trash actions have 44px targets, tooltips and participant-specific accessible labels. Removal still requires confirmation and retains a cancelled response. Participant details use a compact collapsed row. Search covers names, contacts, selections, notes and answers; status filters select active, all, confirmed, waitlisted or cancelled responses. Counts use the complete form; CSV exports all responses and keeps spreadsheet-formula escaping.

## Email preferences

Email alerts are available in the Host dashboard. Owners and accepted co-hosts automatically receive all four alert types for both existing and new forms, without opening settings or saving preferences first: new signups, changes, cancellations and waitlist additions/promotions. Receive signup emails switches all alerts on or off; individual options select the desired activity. Each user saves their own preferences for each form, and saved opt-outs remain in effect. The receiving address comes from the signed-in user's database account, never a submitted email or recipient ID. Saving preferences is explicit and does not change form definitions or participant responses. Automatic enrollment applies to future signup activity and does not send historical signups.

Signup changes enqueue alerts in the same event-row transaction that saves the reservation and signup_forms mirror. Comparisons ignore timestamps and selection/answer ordering, so repeated no-op submissions do not create alerts. Cancelling a reservation also records alerts for participants actually promoted from the waitlist. Alerts work when participant email collection is disabled. They include exact selections/quantities, slot times/timezone, contact details, notes, answers and previous selections/changed details where relevant, with an authenticated View signups link. Participant private management tokens are never included in host mail.

## Storage and processing

`prisma/manual_sql/20261006_signup_host_alerts.sql` creates server-only preferences and outbox tables. Table creation, row-level security and revoked PUBLIC/anon/authenticated grants commit together. The server performs the same idempotent setup when needed; an already installed secure schema skips DDL. No production migration is performed by local tests.

Next's after hook attempts queued alerts after the signup response. The signup result and participant confirmation are independent of host email delivery. Processing rechecks current membership, publication state, account email and preferences before sending. Revoked co-hosts and opted-out recipients are skipped. Atomic SKIP LOCKED claims prevent simultaneous workers sending the same job. Zoho SMTP remains the sole provider, using signup-forms@envitefy.com and the shared Envitefy signature.

Definitive temporary failures use exponential backoff (1, 2, 4, 8 minutes, capped at five attempts). Permanent rejections stop immediately. Failed messages offer an explicit Retry email action to the same authorized recipient. Accepted messages are never automatically resent. A lost SMTP DATA acknowledgement or a sending lease older than five minutes becomes unknown and is held, because resending could duplicate an already accepted email. The recent-attempt list distinguishes pending, sending, provider-accepted, failed, unknown and skipped results; provider acceptance is not an inbox-delivery receipt.

Opening/refreshing alert settings processes due jobs for that form. `/api/internal/signup-host-alerts` provides a protected worker with the existing CRON_SECRET bearer authentication. The checked-in Vercel schedule is a daily fallback, matching the repository's existing cron cadence; normal sends run immediately through after. Pending failures on an otherwise inactive form can wait until that fallback. Deployments requiring faster unattended retry should call the worker every few minutes through their supported scheduler. Processing is bounded by time and batch size; monitor pending/failed/unknown records rather than treating acceptance as proof of receipt.
