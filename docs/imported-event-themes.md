# Imported sports event themes

Sports URL, PDF and image imports share one visual identity pipeline across gymnastics, football and other sports. There are no organizer-specific theme rules.

`source-branding-server.ts` reads bounded inline CSS and up to two likely brand stylesheets through the existing public URL/DNS guard. Public CDN stylesheets are supported. If CSS supplies no colors, it samples up to two labeled logo/background images through that same guard. PDF and uploaded-image imports sample the first two existing page rasters; they do not request another OCR pass. Neutral documents fall back to a sport palette. Source material is evidence, never instructions.

`imported-event-theme.ts` creates a bounded, deterministic recipe from the event title, sport, supplied city, source identity and source palette. Colors, bundled font families and sport motifs are validated; source strings cannot become executable CSS or markup. Body text and accent buttons meet 4.5:1 contrast. A city is used only when supplied in mapped event data. The design is retained in `importedTheme` across map, composition, explicit saves and reloads. Existing saved designs are preserved. Hosts can explicitly create a theme for an older/manual event, Redesign, or switch back to its template style.

## Original artwork

After mapping a fresh private import, the discovery worker prepares one original OpenAI hero using the sport, supplied city, palette and design direction. The text-free brief requires an authentic editorial sports scene and a central focal subject that survives different template crops. The event title is omitted from the image prompt; a city influences the environment only when supplied separately. Neither location, sport, title nor source branding may determine race, ethnicity or other demographic representation. No racial group is required or excluded. The original template photo remains visible while generation runs or fails. If a surface has no template photo, it can use local vector artwork; the gymnastics fallback depicts equipment only. Uploaded artwork always takes precedence.

`sports-artwork-contract.ts` supplies simple preparation scenes and concrete support/equipment constraints for gymnastics, court sports, aquatic sports, cycling, field/rink sports and running, with a generic fallback for other sports. Gymnastics specifically asks for visible feet lengthwise on the beam top, coherent body support, apparatus supports and safety mats. These are composition instructions, not a claim that difficult real gymnastics skills are impossible.

Before upload or application, `imported-event-artwork-review.ts` runs one bounded OpenAI visual check for anatomy, supporting contact, equipment, sport mismatch and unexpected lettering. The checker receives the image and sport, with no city or event title, and must never classify or reject demographic appearance. Clear defects block the image; unavailable/invalid checks are reported separately and also leave the current hero intact. The check has no image-repair or generation capability, and does not guarantee perfect anatomy. No automatic paid regeneration follows rejection.

`imported-event-artwork.ts` atomically claims `importedThemeArtwork` on the saved event before making a paid provider request. Concurrent workers, reloads and resumed imports reuse generating/ready/failed state; a failed request requires explicit Retry. The existing OpenAI image helper uses one high-quality image request with transport retries disabled. The result is decoded and stored as WebP through the existing media uploader. A stale token cannot replace a newer job. Automatic application is restricted to an untouched private import with the same theme. Explicitly saved or published events receive the result in editor memory, and applying it requires an explicit save. Source details and publication do not depend on image-generation success.

The owner-only `/api/events/[id]/theme-artwork` endpoint exposes status and explicit generation/retry. The editor synchronizes results while keeping later host redesigns and uploaded images. New manual designs require a saved draft before an image request so the request can survive reloads. Redesign creates a new theme identity; it does not silently issue an additional image request. Replace event image explicitly requests one new image under a new revision, preserving the existing font, palette, shape, details and current hero until the replacement passes. Applying it to a saved event still requires Save draft/Save changes. Retry clearly states that it generates a new image.

Image requests resolve the saved category through `eventCreationRequirement`, including legacy capitalization, aliases and specialized sports editors. They retain owner-only access and the existing creation authorization check. A signed-in replacement test exposed the earlier case-sensitive category mismatch (`Gymnastics` incorrectly requested `sport-events`); route tests now cover canonical gymnastics, football, other sports and soccer, plus non-owner and non-sports rejection.

Completed images remain available through Use generated image after an unsaved design/reload changes theme identity. This is an explicit image choice, preserving the current design recipe. Each generated file has its claim token in the pathname so reuse of an earlier theme identity cannot overwrite an existing asset. Editor saves cannot overwrite server-owned `importedThemeArtwork`. If a save conflicts, the history client retries once only when its exact loaded baseline differs from the latest event solely in that job field; real content changes, older recovered browser revisions and failed refreshes retain the conflict.

A fresh import has both canonical event fields and the earlier `builderDraft.event` mapping snapshot. Canonical `importedTheme`, including its completed image or an explicit opt-out, takes precedence during editor hydration and render normalization. Otherwise a generated photo can be ready in storage while the page keeps rendering the old fallback. The renderer regression covers this state before the first explicit save.

URL date extraction normalizes abbreviated months such as `Jan.` and `Sept.` before ranking visible date evidence. This lets visible event dates reject conflicting SEO/JSON-LD descriptions even when the visible date uses an abbreviated heading. It does not choose the largest year: historical visible events retain their actual dates.

## Saved event identity

A bare template-gallery entry cannot inherit the ID of the most recently edited saved event. Unsaved browser progress and explicit `draft`/`edit` recovery remain supported. The first explicit draft save updates the editor URL with the returned event ID so reload opens that exact record. This closes the identity-recovery defect found during theme verification.
