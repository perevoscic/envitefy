# Envitefy Create: complete remediation and release plan

Prepared September 19, 2026 as the original plan. Implementation has since started: see the [implementation and release report](create-remediation-implementation.md) for delivered changes, tests and remaining work. This document retains the proposed architecture and acceptance criteria; it is not a completion claim.

The campaign is complete; the product is not ready for release on this evidence. The priority is to repair how Create understands, stores and fulfills a request. Prompt wording is one layer: several failures originate in deterministic parsing, contradictory content rules, output routing, or rendering. A model cannot reliably satisfy a request that the application has already dropped or prohibited.

This plan covers every recorded finding, including historical failures and already fixed regressions. It does not promise that software or image models will never fail. Its objective is to prevent the known failure classes, catch regressions before release, and recover honestly when a provider fails.

## Shared architecture to implement

Extend the existing extraction/edit contracts and fact-preservation safeguards rather than creating a second independent source of event truth. Agree these interfaces before parallel implementation:

| Boundary | Proposed contract | Invariant |
| --- | --- | --- |
| User turn → draft | `TurnIntent` and cited field operations: question, fact change, appearance change, output switch, exclusion or new event; mixed turns can contain several scoped operations | A read-only/capability question cannot change facts; an edit phrased as a question still applies its requested change; a style turn cannot change identity/time |
| Canonical in-memory draft | Versioned `ApprovedEvent`: sourced facts, full people/team identity, semantic kind, output, typed schedule/locations, public content blocks, visual preferences, exclusions and unresolved fields | Supplied facts outrank inferred defaults; unknown, explicit none and explicit removal remain distinguishable |
| Draft → response | Transaction receipt with changed fields, revision, unresolved items, actual capability and persistence status | “Updated,” “saved,” “downloadable” and “included” are supported by the relevant completed operation |
| Draft → output | `OutputPlan`: stable content-block IDs with raster/HTML/details/calendar/download placement, exact wording rules, visual treatment and geometry | Every required block has an appropriate supported destination; no silent loss to private styling metadata |
| Output → image/verification | Immutable `GenerationContract` derived from the approved revision, with allowed/required text, exclusions, subject constraints, dimensions and expected composition | Planner, generation prompt and verifier cannot disagree about whether required text is permitted |
| User edit → implementation | `EditPlan` separating factual changes, page text/layout, actual controls and raster changes | CSS/text edits do not require a new image; late responses cannot overwrite a newer revision; failed candidates do not replace accepted artwork |
| Output → guest actions | `GuestEventProjection`: the same approved schedule, full location, content and capability configuration for display, Calendar, ICS, Directions, RSVP and download | A displayed 2 PM meet cannot export noon; supplied venue and room cannot disappear from the export |

These are proposed interfaces, not additional database tables required by default. Keep new progress in memory until explicit Save or Publish. Add versioned, backward-compatible normalization for existing saved JSONB payloads; preserve canonical event fields, legacy route/data compatibility and both history/dashboard cache invalidation where needed. A rollout must not rewrite existing events, replace accepted artwork, or silently invent missing legacy data.

### Prompt and conversation changes

1. Extraction requests cited changes against the current approved revision, not a wholesale rewritten draft. Treat uploaded/quoted content as evidence, never as instructions that override the user. Reject unrelated model changes even when the model returns syntactically valid JSON.
2. An explicit title, date, selected product, contact or required wording is authoritative. Date-only input cannot replace the clock; a theme inspired by another category cannot change the event; “teens 13+” is eligibility, not a person's name and age.
3. Keep practical guest instructions out of visual-style and gift fields. Preserve exact slogans, punctuation, bilingual line breaks and explicit exclusions. Record semantic wording separately from text that must be exact.
4. Ask only for genuinely necessary unresolved details. Do not repeatedly request optional guest counts, invent an end time or re-ask answered facts. A conflict question identifies the conflicting facts and preserves the rest of the draft.
5. Generate the assistant response from the actual transaction receipt and a tested capability registry. A read-only Q&A answer leaves the draft unchanged; “in this chat” differs from “saved.” Explain format capabilities accurately, including a static Flyer's real download and a page's actual working controls.
6. Creative planning chooses approved content-block IDs and supported layouts. The application rejects contradictory text allowlists, absent required copy, unsupported output switches and invalid geometry before a paid call. Compare against independently captured original user requirements, not just the model's extracted fields: a fact omitted during extraction can otherwise look complete downstream. Preserve unresolved source requirements and ask a precise clarification when needed. Do not solve conflict by silently deleting a user requirement.
7. Appearance requests are split by responsibility. Event Page font/color/layout changes modify HTML/CSS. Actual image composition/color changes use the image path. For text-bearing Live Cards/Flyers, keep approved facts and required text in the shared contract; never remove the street address because a different product normally omits it.
8. Verification checks the whole deliverable contract, including prohibited fake controls and prior defects, while attributing each failure to the responsible layer. Model-only pixel issues may receive the bounded targeted repair already supported. Contract or CSS defects should not trigger repeated paid image attempts. Preserve diagnostic issues, original artwork and a clear recovery action.

A compiled prompt passing these checks proves valid instructions were sent. It does **not** prove that a future image model rendered the requested words or composition correctly. Keep that distinction in reports and release decisions.

## Verification without new art

| Layer | What to execute | What this proves |
| --- | --- | --- |
| State and conversation | Captured transcript + extraction response replay; faulty full-draft patches; questions, negations, clears, mixed edits, stale/concurrent responses and fallback paths | Facts, identity, exact copy and outputs survive the real merge path; the streamed assistant is grounded in actual state |
| Prompt and contract | Build actual generation/edit/verification payloads for each case; compare required content sets, placement, prohibited content and dimensions; inject contradictory plans | The code cannot silently promise/exclude the same text or route a page-font change to a text-free image |
| Browser and renderer | Feed archived WebPs to the actual chat preview, category/page renderer and guest flow at 320/360/390/430/768/1440 CSS px, both orientations and 200% zoom | CSS cropping, title contrast, overlap, missing DOM content and control behavior can be fixed without regenerating art |
| Guest APIs and exports | Isolated database/blob namespace and local mail sink; actual RSVP success/error persistence; parse ICS/URLs; trigger and inspect downloaded files | Actions produce the requested data and actual artifacts; no real guest receives test messages |
| Compatibility and lifecycle | Existing saved payloads, explicit save/restore, Save and leave, Discard and leave, Keep editing, reload warning, failed save, cancellation, retry and navigation | No accidental draft creation, loss of a previously saved draft, stale replacement or unexpected publication |
| Regression and engineering | Existing `npm run test:create-facts`, campaign harness suite and targeted affected suites; Biome and editor diagnostics after TS/TSX changes; independent type checking plus production build | Guards remain intact. `next build` alone is insufficient because TypeScript build errors are ignored by configuration |

Use behavior checks and parsed values, not source-string assertions or merely “no horizontal overflow.” Capture computed styles for contrast and image bounds for cropping. Keep useful existing source guards, but do not weaken them simply to get green. The plan's accessibility target is readable contrast, labeled controls, 44px product tap targets and fully visible keyboard focus; distinguish that product target from the narrower WCAG AA focus-not-entirely-obscured requirement.

Archived images with missing text or fake buttons remain negative fixtures. They can prove that a new verifier rejects the defect or that a preview displays the entire original image; they cannot prove a newly correct image exists. Existing golden/negative fixtures must be hash-locked. The offline harness should fail immediately on any attempted live provider request.

## Classification, closure and reporting

Every register row receives one or more work packages and keeps the original finding ID and evidence. The register distinguishes:

- **Observed product issue:** reproduce on the frozen implementation baseline, fix, and verify at the original scope plus related categories/formats.
- **Historical regression:** retain the old failure and replay it; a successful later journey does not alone prove that failure class is fixed.
- **Bounded verified fix:** keep the existing guard and re-run it. A prior unit-level slogan fix does not close a later image's missing slogan.
- **Corrected checker result:** retain the raw failure and the independent adjudication together; fix or guard the checker rather than manufacture a product bug.
- **Infrastructure/operational stop:** preserve 503s, invalid responses, response-body eviction, harness interactions, controlled stops and budget limits. They are not visual-quality verdicts. Verify bounded waiting, cleanup and resumption.
- **Unverified observation:** perform the specified investigation before calling it a confirmed defect. For example, an aspect-ratio change alone is not proof of unacceptable composition.

For the screenshot's `failed` / `needs_review` ambiguity, GR11 should show separate columns for **journey checkpoint**, **review completion**, and **quality verdict**, explain recovered-original versus successful-edit outcomes, and separate latest results from archived attempts. The original browser checkpoint may be “awaiting review”; a completed independent review must not still look pending. Preserve the original evidence and quality failures. Historical first-cycle limitations already labeled as historical are not a new report bug.

A finding closes only with: linked original evidence; a before/after behavior test; code/PR and source revision; original and affected-cross results; independent review for P0/P1; and migration/compatibility evidence where applicable. A reviewer may prove a raw observation was a checker artifact, but must record the reason and supporting evidence. Every confirmed flaw is fixed, not waived by averaging scores. Overall campaign scores never substitute for required-case acceptance.

## Deployment gates and rollback

1. **Traceability:** every finding, historical regression and Q&A assertion is assigned. No orphan cases, invalid evidence links or unresolved contradictory classifications.
2. **Request integrity:** 100% of the 93 offline briefs preserve selected format, supplied title/identity, approved clock/timezone, locations, required content and explicit exclusions, measured against independently recorded original briefs rather than self-certified extracted state. Every required content block has a verified destination. No invented facts or unacknowledged fallback.
3. **Deliverable integrity:** actual previews match the published renderer; archived complete artwork is not accidentally clipped; essential copy is readable and unobscured; Calendar/ICS/Directions/RSVP/download pass their real contracts. Errors preserve user work and offer an accurate next step.
4. **Lifecycle and compatibility:** explicit-save behavior, old saved events, category capabilities and permissions pass. Existing routes/data keys stay compatible; unsaved progress is not persisted by a new telemetry or revision mechanism.
5. **Operational readiness:** independent type/lint/targeted tests and production staging checks pass; provider retries/timeouts/cancellation are bounded; logs correlate turn, draft revision, output contract, generation/edit and verification outcomes while excluding private message/contact content. Track mismatch/rejection rates, missing-copy blocks, failed actions, fallback use, latency and per-operation spend.
6. **Provider quality remains a separate gate:** first qualify the revised real streaming chat, extraction and persona behavior with a capped text-only live run and image endpoints blocked; mocked replies cannot prove prompt understanding. Separately, the current campaign's rejected edits and incorrect pixels are not repaired by a prompt snapshot. After offline fixes, qualify affected image paths with a later bounded live canary before claiming image-model readiness. Neither run happens now. Real participant sessions are also needed before claiming expectations are met for actual moms, teachers, coaches and gymnasts.
7. **Rollback:** gate the new contract by a versioned rollout switch; retain the previous renderer/reader path for compatible existing events. Preserve accepted assets and explicit saves. Halt expansion on fact/output mismatch, required-copy loss or broken actions; disable the affected generation path with a truthful message rather than knowingly routing users through a corrupting fallback. Record the failing revision and reproduce it offline before resuming.

Additional coverage is required for uploads/reference fidelity, existing-event redesign, broader languages/locales, DST/multi-day schedules, interrupted networks, sign-up capability questions and controlled real integrations. These are labeled coverage gaps, not bugs claimed from unrun tests. See the guest workstream's follow-up list. Transactional email integration continues to use Zoho SMTP and the existing sender/guest-privacy rules.
